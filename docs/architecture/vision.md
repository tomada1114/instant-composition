# Vision

## The product

Instant Composition starts as one drill: a Japanese sentence appears, the learner says
it in English before a timer runs out, then checks the model answer and grades
themselves. It grows into a language-learning platform built from several **activities**
that share one picture of the learner:

- **Activities.** Instant composition first, vocabulary second (a rebuild of a separate
  prototype, not a port of its code), and further activities later. Each activity owns
  its own session mechanics; all of them feed and read the same learning record.
- **Languages.** Today every item pairs a Japanese prompt with an English answer, and
  the UI is Japanese only. The target is any **language pair** — more L1s (a Chinese or
  Spanish speaker learning English) and more target languages (a Japanese speaker
  learning Chinese or Spanish). Items are anchored on the target-language sentence, with
  a prompt and an explanation per L1
  ([ADR-0004](adr/0004-multi-language-content-model.md)).
- **Clients.** A web SPA first, then native apps — Swift for iOS and macOS, Kotlin for
  Android — all talking to one versioned HTTP API. Deck composition, scheduling and
  grading stay on the server, so a client renders and collects answers without knowing
  the rules or the infrastructure
  ([ADR-0001](adr/0001-server-owned-logic-behind-one-api.md)).
- **Personalization.** A learner model — which grammar points, words and topics a
  learner is weak on — built first from rules over the learning record, later from
  structured LLM feedback on typed answers, and fed back into what each activity deals.
- **Audience.** Public, with self sign-up. Payment is expected to go through Stripe on
  the web and the platform stores in the native apps; whether LLM features are metered
  as a monthly allowance or as prepaid credits is still open
  ([ADR-0010](adr/0010-entitlements-and-billing.md)).

The first public release is deliberately LLM-free. The owner wants to use the drill on
real infrastructure, with real sign-in, long enough for the foundation to settle before
language models add cost, latency and a new failure mode.

## Guiding principles

Each principle is here because it changes a concrete decision. A principle that did not
would be decoration.

### Evaluation sits at the center of every LLM feature

An LLM feature is not done when it works on a demo; it is done when its quality can be
stated as a number and a change that lowers that number fails CI. Here that means an
in-repository evaluation harness per LLM task, gold sets built from assets that already
exist (2,052 reviewed alternative answers, 324 deleted cards with the reason each was
rejected), agreement with human labels and the rate at which repeated grading of the
same input flips, and a CI gate on any change to a prompt, schema or model setting
([ADR-0011](adr/0011-llm-integration-and-evaluation.md)). It also sets the order: no
language pair launches until its automated review gate passes, because the owner cannot
read every language the platform will teach.

### Delegated authority is explicit and tested

Authentication (who is calling) and authorization (what this caller may do, on whose
behalf) are separate. A request becomes a `RequestContext` carrying an **Actor** — a
learner, a system job, or later an agent acting for a learner — and every store a
service receives is already bound to one LearnerId, so code cannot even express a read
of another learner's data. An isolation contract test writes as one learner and reads as
another through every store method, against every adapter
([ADR-0005](adr/0005-identity-and-authorization.md)). An agent tool never takes a
learner id as an argument; the learner comes from the verified session.

### Cost is explainable per request and per feature

Every billed call records model, feature, token counts and an estimated cost against the
learner who caused it, so "what does one graded answer cost" and "what does feedback
cost per month" have answers. Components with a minimum monthly fee — NAT gateways, load
balancers, provisioned search clusters — are avoided; the target topology runs on
request-priced services behind a flat-rate CDN plan, and AWS Budgets exist before the
first deployed resource
([ADR-0009](adr/0009-aws-topology-environments-and-operations.md)).

### Synchronous paths stay fast; heavy work is an idempotent job

The timed drill never waits on a language model. Grading, feedback and learner-model
updates run after the answer is stored, as jobs keyed by the answer id they concern, so
a retry or a duplicate delivery returns the stored result instead of paying for a second
call. The same job function runs inline locally and behind a queue in production.
Idempotency already has a foothold: answer ids are generated by the client and a resend
is ignored (`src/core/types.ts:41`, `src/server/db/answers.ts:49`).

### LLM output is structured

Every LLM task declares its output as a schema — derived from the same zod definitions
the API uses — and receives JSON that conforms to it. Free text never crosses into
domain code; a grade, an error tag and an explanation are separate typed fields.

### Every call is observable

A request carries a request id through logs; an LLM call additionally reports model id,
prompt version, input, output and cache token counts, latency and cost estimate. The
unit of observation is the single call, because that is the unit a regression or a cost
spike has to be traced back to.

### Defenses sit at the entry and the exit, and attacks are test data

Learner text is data, never instructions: it is passed in a delimited field, the grader
has no tools, and its output is constrained by schema, so a successful injection can at
worst misgrade the attacker's own answer. The larger risk is cost abuse, which input
limits and the entitlement ledger bound. Adversarial inputs — injections hidden in an
answer, off-language answers, empty or oversized ones — are part of every evaluation
set, not an afterthought.

### What breaks often is separated from what must never be lost

Learner data, identities and the content catalog change rarely and must survive any
redeploy; the API, the web client and later the agents are rebuilt constantly. They live
in separate infrastructure stacks, and dependencies point one way — the volatile stack
reads the stable one, never the reverse
([ADR-0009](adr/0009-aws-topology-environments-and-operations.md)). The same rule
governs the code: `domain` depends on nothing, `application` on `domain`, adapters and
apps on both ([ADR-0002](adr/0002-architecture-style-and-repository-layout.md)).

### Configuration comes from outside, secrets through one door

A build is environment-agnostic; environment-specific values are read at startup, and
one module per deployable validates them. Secrets reach the process only through that
module, which is what makes "where does this credential enter" a one-file question. This
continues a rule the codebase already follows: `src/server/env.ts` is the only reader of
`process.env` (`src/server/env.ts:128-133`).

### Depth over breadth, with the reasoning written down

One application built with care beats several built quickly. Every decision that a
reviewer could reasonably contest has an ADR stating the alternatives and why they lost,
so the design can carry a long technical discussion without relying on memory.

## Owner constraints

- **Sequence.** Infrastructure and authorization first; the application is used LLM-free
  for a while; LLM features, AgentCore and automated card generation come later.
- **Production level: "portfolio grade".** Separate AWS accounts per environment (still
  under discussion, [ADR-0009](adr/0009-aws-topology-environments-and-operations.md)),
  infrastructure as code with CI deployments, monitoring and alerts, point-in-time
  recovery for the database, account deletion and data export. Cognito's paid threat
  protection waits until abuse is actually observed; restore drills and SLOs are not yet
  in scope.
- **Budget.** Fixed costs up to tens of thousands of JPY per year are acceptable, which
  is enough for a paid CDN tier or monitoring but not for always-on compute.
- **Stack.** No attachment to the current framework. The criteria are fitness for the
  target and how easily AI coding agents can work in the code: explicit data flow, few
  framework conventions to get wrong, and fast, deterministic tests.
- **Rewrite.** The current code was a provisional make-it-work version and may be
  rewritten wholesale — in this repository, incrementally, keeping its gates, its card
  tooling and its history.
- **Public repository.** Everything here is written to be read by strangers.

## Non-goals

- **Microservices.** One deployable application core, invoked by an API function and
  later a worker. Splitting services buys independent scaling and team autonomy, neither
  of which a one-owner project needs, at the price of distributed failure modes.
- **Client-side deck composition.** Three client platforms in three languages would each
  need an identical copy of the dealing and scheduling rules. The server decides;
  offline clients queue answers against decks fetched while online
  ([ADR-0007](adr/0007-http-api-contract-and-offline-sync.md)).
- **Realtime or social features.** No multiplayer, chat between learners or live
  leaderboards; nothing in the learning loop needs them.
- **Hosting or fine-tuning our own models.** Models are consumed through Amazon Bedrock;
  the leverage is in evaluation and prompt design, not in operating inference.
- **An agent in the core loop.** Grading, feedback and card generation are fixed
  workflows with structured input and output. An agent runtime is adopted only for a
  feature that genuinely needs open-ended, multi-turn tool use
  ([ADR-0012](adr/0012-agents-and-agentcore.md)).
